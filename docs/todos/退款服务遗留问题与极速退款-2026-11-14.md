## 一、极速退款（已实现）

### 1.1 定义

未发货订单的「仅退款」在用户提交后自动完成：售后审核 → 创建支付退款单 → 支付退款审核 → 原路退回 → 售后单完成。命中规则的退款单 `refunds.is_express = true`。

### 1.2 准入规则

| 条件 | 规则 |
|------|------|
| 退款类型 | 必须是「仅退款」 |
| 发起人 | 用户自助申请（运营代发起不走极速） |
| 履约方式 | 快递（`Mail`） |
| 订单状态 | `Paid` / `Preparing`（未发货） |
| 开关 | 平台开关 + 店铺开关同时开启 |
| 支付通道 | 存在 `balance` / `wechat` 的已支付支付单 |
| 单笔金额 | ≤ min(店铺上限, 平台上限)，0 表示不限制 |
| 单日次数 | 单用户当日极速退款次数 < min(店铺上限, 平台上限) |

### 1.3 执行链路

```
用户申请（Apply）
  ├─ 计算金额 / 运费
  ├─ ExpressRefundRule 判定 → refunds.is_express
  └─ 仅退款自动审核 → Processing
RefundInitialized（ShouldDispatchAfterCommit）
  └─ ExpressRefundOnInitialized → ProcessExpressRefundJob（队列）
       └─ RefundActions\Express
            ├─ Process：创建支付退款单（Pending）
            ├─ PaymentRefundService::autoApprove()：Pending → Approved（approved_by 为空）
            └─ PaymentRefundService::execute()：原路退回
                 ├─ 余额：即时完成 → PaymentRefundCompleted
                 ├─ 微信 SUCCESS：完成 → PaymentRefundCompleted
                 └─ 微信 PROCESSING：支付退款单保持 Processing（见遗留问题 1）
PaymentRefundCompleted → CompleteRefundOnPaymentRefundCompleted → 售后单 Completed
```

通道异常时：售后单置 `Failed`，后台用现有「重新发起退款」（`ReRefund`）重试；重复任务幂等。

### 1.4 配置

平台兜底（`config/custom.php` → `mall.express_refund`，对应 `.env`）：

| 配置 | 环境变量 | 默认 |
|------|----------|------|
| 总开关 | `MALL_EXPRESS_REFUND_ENABLED` | `true` |
| 单笔上限 | `MALL_EXPRESS_REFUND_MAX_AMOUNT` | `500` |
| 单日次数 | `MALL_EXPRESS_REFUND_DAILY_LIMIT` | `5` |

店铺级（`store_configures` / 租户「店铺配置 → 售后」）：

| 字段 | 语义 |
|------|------|
| `express_refund_enabled` | 店铺极速退款开关，默认关 |
| `express_refund_max_amount` | 单笔上限，0 = 仅受平台上限约束 |
| `express_refund_daily_limit` | 单用户单日次数，0 = 仅受平台上限约束 |

### 1.5 相关代码

| 位置 | 作用 |

### 1.7 已知限制

- 依赖队列（Horizon）常驻；队列未启动时退款单停在 `Processing`。
- 微信返回 `PROCESSING` 时无自动收口，需人工或遗留问题 1 处理。
- 规则在事务内判定，同一用户并发提交时单日次数上限存在极小概率穿透（软限制）。

## 二、遗留问题（待排期）

### T1 微信退款异步结果无收口（P0）

**现状**
- `WechatPaymentService::refund()` 只读取同步响应 `SUCCESS` / `PROCESSING`。
- `PaymentRefundService::refundToWechat()` 对 `PROCESSING` 仅落 `PaymentRefund::Processing` + `channel_refund_no`。
- 无 `notify_url`、无退款回调路由、无退款查询方法、无对账任务。

**影响**
- 资金已退但系统停在「退款处理中」：库存不回补、优惠券/秒杀不释放、订单不置 `Refunded`。
- 财务只能人工核对，量大必漏；极速退款体验卡死。

**方案**
- [ ] `WechatPaymentService::refund()` 增加 `notify_url`，`PaymentRefundService` 传入 `route('api.finance.payment-refund.notify')`。
- [ ] 新增退款回调路由与控制器方法：`lock:` 中间件防重放、验签、按 `out_refund_no` 查 `payment_refunds`（不依赖租户上下文）。
- [ ] `SUCCESS` 复用 `PaymentRefundService::complete()`；`CLOSED/ABNORMAL` 置 `Failed` 并写日志。
- [ ] 新增 `WechatPaymentService::queryRefund()`（`GET v3/refund/domestic/refunds/{out_refund_no}`）。
- [ ] 新增对账命令 `finance:reconcile-payment-refunds`：扫描超时的 `Processing` 微信退款，回写最终状态；超 24h 未成功写告警；`routes/console.php` 每 5 分钟 `onOneServer()`。

**验收**：验签失败拒绝、重复回调幂等、SUCCESS 完成售后单、CLOSED 转失败；极速微信处理中 → 回调 → 售后单 `Completed`。

**工作量**：2.5d（回调 1.5d + 对账 1d）

### T2 分摊尾差 0.01（P1）

**现状**
- `Apply::netUnitPrice()` 把 `net/qty` 截断到 2 位；剩余金额按 `unitPrice × refundedQty` 扣减，本件金额被剩余封顶。
- 例：100.00 元 / 3 件，单价 33.33，退完 3 件只退 99.99，`0.01` 永远退不出。

**影响**：整单退款后累计退款 < 实付，订单已判 `Refunded` 但账不平。

**方案**
- [ ] `Apply::calculateRefundAmount()`：本笔退完订单项全部剩余数量时，`itemAmount` 直接取 `remainingAmount`（尾差随最后一件退出）。
- [ ] 回归 `UpdateAmount` 上限校验；补充多次部分退款后全额退款的用例。

**验收**：3 件 100 元、5 件 99.99 元、多次部分退款后全额退款，累计退款 == 订单实付。

**工作量**：0.5–1d

### T3 用户通知缺失（P1）

**现状**：`RefundCompletedNotification` 已存在但无监听器；`RefundInitialized`、`RefundFailed` 也无监听，用户只能主动刷新。

**方案**
- [ ] 新增 `RefundCompletedListener`（`RefundCompleted` → `notify`，`try/catch + report`，对齐 `OrderPaidListener`）。
- [ ] 新增 `RefundFailedListener`（失败/极速失败提示）。
- [ ] 视产品需要决定是否通知「申请已受理」。
- [ ] 确认渠道（站内信 / 短信 / 公众号模板消息）；回调链路中建议 `ShouldQueue`。

**验收**：完成/失败各一条通知；极速退款完成后用户可收到；通知失败不影响退款状态。

**工作量**：0.5–1d（渠道确认占大头）

---

### T4 金额 float → string（P1）

**现状**：`PaymentRefundService::create(..., float $amount, ...)`；`RefundActions\Process` 把 `refund->total` 转 `(float)` 后 `bccomp`；其余链路已用 bcmath 字符串。

**影响**：边界金额（差 0.01）可能误判；后续接支付宝/分账/手续费会放大。

**方案**
- [ ] `create()` 改 `string $amount`，内部不再转 float。
- [ ] `Process::createPaymentRefund()` 直接传 `(string) $this->refund->total`。
- [ ] 同步调整 `PaymentController::refund` 与相关测试。
- [ ] 可选：`PaymentRefund` 增加字符串读取辅助，避免视图 `(float)`。

**验收**：现有 `PaymentRefundServiceTest` 全绿 + 0.01 / 99.99 / 100.00 边界用例。

**工作量**：0.5d

### T5 状态语义收敛（P2，3 个子任务）

**T5.1 `Retry` 与 `ReRefund` 语义重叠**
- 现状：`retryRefund()` 只把售后单 `Failed → Processing`，支付退款单仍 `Failed`，资金不会自动重试，形成悬挂单。
- [ ] 让 `Retry` 委托 `ReRefund`，或后台只保留「重新发起退款」入口。
- 验收：失败单重试会重跑通道，不再悬挂。工作量 0.5d。

**T5.2 `Received` 死状态**
- 现状：枚举/状态机/筛选仍包含 `Received`，但 `ConfirmReceive` 直接 `Shipping → Processing`。
- [ ] 保留枚举做历史兼容并移除流转，或一次性迁移 `Received → Processing` 后删除（评估 event_logs 旧状态）。
- 工作量 0.5d（含数据迁移与回归）。

**T5.3 `Failed` 归类与可删除性**
- 现状：`ofProcessing` 含 `Failed`、`ofClosed` 不含，`Destroy` 不允许删 `Failed`，失败单常驻「处理中」。
- [ ] 新增「退款失败」scope/tab；允许软删 `Failed`，或归入「已关闭」并保留重试入口。
- 工作量 0.5–1d。

### T6 组合支付不支持（P3，需业务确认）

**现状**：`Process::createPaymentRefund()` 只在单张支付单上找「可退额度 ≥ 本笔退款」的记录，否则抛「该订单没有可退款的支付单」；极速退款会落到失败分支。

**先确认**：业务是否允许一张订单存在多张已支付支付单（混合支付/拆单/补差价）。

**方案**
- [ ] 若不允许：在 `Process` 给出明确提示 + 后台人工处理入口（0.5d）。
- [ ] 若允许：按支付单拆分创建多条 `PaymentRefund`；完成判定改为「该售后单下所有支付退款单 Completed」；部分失败保持 `Processing` 并支持单条重试（2–3d）。
- 验收：混合支付订单可整单退回；部分失败不误完成售后单。
