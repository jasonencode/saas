## 二、P0 —— 资金丢失、重复或错付

### [x] PAY-01 `tenant_id` 恒为 null，微信商户配置靠「随便取一条」，充值会打进任意租户商户

- **文件**：`app/Http/Controllers/Finance/RechargeController.php:46`；`app/Http/Controllers/Finance/PaymentController.php:58,159,212,282`；`app/Models/Traits/BelongsToTenant.php:31-38`；`app/Services/Finance/PaymentRefundService.php:475-477`；`app/Console/Commands/Finance/ReconcilePaymentRefundsCommand.php:76-78`
- **现状**：
  - `RechargeController::store()` 使用 `Auth::user()?->tenant_id`，但 `users` 表没有 `tenant_id`（租户关系在 `user_tenant`），取值恒为 `null`。
  - `PaymentController::store()` 未传 `paymentable` 时同样写 `null`；关联充值单时继承充值单的 `null`。
  - `BelongsToTenant::ofTenant(null)` 是**空操作**：`WechatPayment::ofTenant(null)->first()` 会取到全平台任意租户的商户配置。
  - 三处选取口径还不一致：支付/回调 `first()`，退款/对账 `orderByDesc('status')->first()`。
- **失败场景**：
  - 用户充值 100 元，微信下单落到租户 A 的商户号；平台侧以为进入平台账户，实际进入 A 的商户账户，对账无法配平。
  - 回调若刚好取到另一条配置 → 验签失败，回调永远 `FAIL`，充值不到账且微信持续重试；用户钱已被扣。
  - 退款按 `status desc` 取配置，可能与原支付商户不同 → 微信退款失败或打错商户。
  - 极端链：充值/裸支付单 `tenant_id=null`，若平台第一条商户配置属于可自管证书的租户，该租户可伪造签名回调把未支付充值单标记成功，直接给余额入账（与 PAY-15 组合）。
- **建议**：
  1. Finance 统一使用 `TenantResolver::current()?->getKey()`（或校验 `user_tenant`）写入 `tenant_id`；无租户上下文时**禁止**创建微信支付单。
  2. `ofTenant(null)` 显式抛异常，避免静默全表。
  3. `payment_orders` 增加 `wechat_payment_id`（下单时锁定配置），回调/退款/对账只使用该配置，不再按租户猜。
  4. 抽 `WechatPayment::activeForTenant()` 统一「启用优先 + 唯一」的选取口径。

### [x] PAY-02 支付退款单仍可软删，且可退额度不统计软删记录，删一笔即可重复退款

- **现状**：两侧财务面板（运营端/租户端）共用 `RefundsTable`，仍保留 `DeleteAction`、`DeleteBulkAction` 与 `TrashedFilter`；`PaymentRefund` 使用 `SoftDeletes`；`PaymentOrder::refunds()` 与 `refundableAmount()` 都**没有 `withTrashed()`**。
- **失败场景**：100 元支付单全额退款完成 → 财务删除该退款单 → `refundableAmount()` 重新变回 100 → 可再次创建退款并原路退回，**同一笔支付退两次**；审计链同时被删除（`TrashedFilter` 还能恢复，但额度已恢复）。
- **建议**：

  2. `refundableAmount()` 与所有额度统计一律 `withTrashed()`。
  3. 数据库补「同一支付单已退金额 ≤ 支付金额」的汇总约束或对账任务。

### [x] PAY-03 充值到账链路无行锁/无条件更新，可能重复入账或「渠道已收款、余额永不到账」

- **文件**：`app/Services/Finance/RechargeService.php:71-116,128-149`；`app/Services/Finance/PaymentService.php:142-164`；`database/migrations/0001_01_00_000001_create_user_accounts_table.php:40-69`
- **现状**：`markPaid()` 先读 `$order->status` 再 `$order->update()`，`complete()` 同样先读 Paid 再入账；两者都没有行锁或条件更新；`user_account_logs` 没有 `(source_type, source_id, type)` 唯一约束。
- **失败场景**：
  - 同一充值单存在两张支付单时，两个回调并发：各自锁的是**不同支付单**，都读到充值单 `Pending` → 都记 Paid → 都 `complete()` → 余额重复入账（`user_account_logs` 出现两条同源充值）。
  - 串行回调：第二张支付单的 `markPaid()` 抛「充值订单状态不正确」，整个事务回滚 → 支付单回到 Pending，渠道已收款但本地永远不到账，微信无限重试。
- **建议**：
  1. `markPaid()`/`complete()` 改为 `where status = Pending/Paid` 的条件更新并判断影响行数；`complete()` 内锁定充值单与账户。
  2. `recharge_orders.payment_no` 或账户流水补唯一约束；同一业务单只允许一条成功入账。
  3. 创建支付单时按 `paymentable` 做待支付判重（见 PAY-07）。
- **备注**：FIN-04 仍存在；单测只覆盖「同一支付单重复回调」，未覆盖「同一充值单两张支付单」。

### [x] PAY-04 微信支付回调不校验金额/币种，改运费或旧 prepay 会造成少收/多收

- **文件**：`app/Http/Controllers/Finance/PaymentController.php:220-251`；`app/Services/Mall/OrderActions/UpdateFreight.php:82-85`；`app/Services/Finance/PaymentService.php:68-69`；`app/Services/Finance/PaymentRefundService.php:483-490`
- **现状**：回调只比对 `out_trade_no`，不比对 `amount.total`、`currency`、`mchid`；`UpdateFreight` 只改 `payment_orders.amount`，不关闭旧微信 prepay；余额支付会重算金额，微信回调不会。
- **失败场景**：用户先拿到 98 元的微信 prepay，商家随后把运费从 10 改成 30（订单应付 118，支付单同步为 118），用户仍按旧 prepay 支付 98 → 回调 `SUCCESS`，订单置为已支付，平台少收 20 元；反向改价则多收，需要人工退款。
- **连带问题**：退款时 `totalAmount` 取的是被同步后的 `payment_orders.amount`（118），而微信实际交易总额是 98，退款会因总金额不一致被拒。
- **建议**：
  1. 回调校验 `amount.total === (int) bcmul(payment.amount, 100, 0)` 且 `currency === 'CNY'`；不一致时落审计、告警并人工/自动处理，不能直接置 Paid。
  2. 已生成 prepay 后禁止原地改金额：改运费时作废旧支付单并新建，或调用微信关单接口（当前 `WechatPaymentService` 没有 `close()`）。
  3. 支付单金额一旦生成 prepay 即视为快照，退款总额以微信交易总额为准（落库 `transaction_id`/实收金额）。

### [x] PAY-05 创建支付单不校验 `paymentable` 归属，可绑定他人订单/充值单

- **建议**：`resolve()` 增加 `user_id`（及租户）约束，控制器在创建前断言 `paymentable->user_id === Auth::id()` 且租户属于当前上下文；越权返回 404。

### [x] PAY-06 待付款订单可删除/取消后，遗留的支付单仍可付款，回调无业务可推进且不退款

- **文件**：`app/Services/Mall/OrderActions/Delete.php:44-64`；`app/Services/Mall/OrderActions/Cancel.php:55-72`；`app/Enums/Mall/OrderStatus.php:174-177`；`app/Services/Finance/PaymentService.php:142-164`
- **现状**：`Pending`/`Canceled` 订单允许删除（软删），删除/取消都**不处理**该订单的 `Pending` 支付单，也不关闭微信 prepay；`markPaidWithBusiness()` 用 `$payment->paymentable` 取业务，软删订单返回 `null` 后既不推进业务，也不创建退款，只把支付单置 Paid。
- **失败场景**：用户下单 → 获取微信支付参数 → 删除订单（或订单被取消）→ 用户在 prepay 有效期内付款 → 回调验签通过、支付单 `Paid`，但 `paymentable` 为 null：订单不存在、钱已收、无退款单，用户只能投诉。
- **建议**：
  1. 删除/取消订单前检查是否存在 `Pending` 支付单：存在则先作废支付单并调用微信关单，或禁止删除。
  2. `markPaidWithBusiness()` 在 `paymentable_type` 非空但 `paymentable` 为 null 时，直接创建「无业务来源」的退款单并高优先级告警，不能静默置 Paid。
  3. 订单 `user` 被软删导致 `RuntimeException` 时同样落退款，避免回调无限 FAIL。
  4. 补回归用例：删除待付款订单后回调仍应退款。

### [x] PAY-07 创建支付单无判重、不校验业务可支付状态，重复收款后只能挂人工退款

- **文件**：`app/Http/Controllers/Finance/PaymentController.php:40-82`；`routes/apis/finance.php:41-42`
- **现状**：同一 `paymentable` 可反复 `POST /api/payments` 生成多张 Pending 支付单；创建时不校验订单是否仍为 Pending、是否已过期、是否已支付、充值单是否仍待支付。仅有的 `lock:payment_create,10` 只防 10 秒内重复提交。
- **失败场景**：用户对同一订单创建两张支付单并都付款 → 第二张回调触发 `OrderNotPayableException`，系统自动创建**待财务审核**的退款；在审核前用户资金被占用，且需要人工处理。充值场景见 PAY-03。
- **建议**：创建前 `exists()` 判重并复用/关闭旧单；校验 `paymentable` 的可支付状态与 `expired_at`；为 `(paymentable_type, paymentable_id, status)` 增加部分唯一索引或应用层锁。

### [x] PAY-08 余额支付先扣款、后判断业务是否可支付，失败才走人工退款

- **文件**：`app/Services/Finance/PaymentService.php:56-90`（扣款在 77-84，业务推进在 89）
- **现状**：`payByBalance()` 在锁内只校验支付单状态与金额，不校验订单/充值单是否仍可支付；真正不可支付时由 `OrderService::pay()` 抛异常，再自动创建 Pending 退款。
- **失败场景**：订单已取消/已支付后用户重复提交余额支付 → 余额先被扣，随后只得到一张待审核退款单；财务未处理前用户可用余额减少，体验与投诉风险高。
- **建议**：在扣款前用与 `OrderService::pay()` 一致的口径预检 `paymentable` 状态（锁内）；对「已取消/已支付」直接拒绝，不产生资金动作。

### [x] PAY-09 支付密码无失败计数/锁定，锁粒度按支付单可绕过

- **文件**：`routes/apis/finance.php:47-49`；`app/Http/Middleware/EnsureSingleRequest.php:48-55`；`app/Services/Finance/UserAccountService.php:221-228`；`app/Http/Requests/Finance/PayPaymentRequest.php:18`
- **现状**：`pay` 路由锁 key 为 `payment_pay_{paymentId}`，按单不按人；密码校验无失败次数、无退避/锁定；`PaymentPasswordRule` 只校验格式（可空）。

- **备注**：FIN-05 仍存在。

### [x] PAY-10 退款回调/对账不认领「本地 Failed、渠道 SUCCESS」的退款，资金已退但本地永远失败

- **文件**：`app/Http/Controllers/Finance/PaymentController.php:310-320`；`app/Services/Finance/PaymentRefundService.php:317-334,346-362`；`app/Console/Commands/Finance/ReconcilePaymentRefundsCommand.php:41-49,90-107`
- **现状**：`refundNotify` 只在状态非 Completed 时调用 `complete()`，而 `complete()` 只接受 `Processing`；对账命令也只扫 `Processing` 的微信退款。
- **失败场景**：微信退款实际已受理，但本地因网络超时/异常记为 `Failed`（`execute()` 的 catch 分支）；随后微信发送 SUCCESS 回调 → `complete()` 条件更新 0 行 → 抛异常 → 返回 `FAIL`，微信持续重试；对账命令不扫 Failed，永远无法自愈。售后单可能长期停在失败，而钱已经退回。
- **建议**：
  1. SUCCESS 回调对 `Failed` 退款先 `queryRefund()` 核对，确认成功后允许 `Failed → Completed`（并同步售后单）；不能只认 Processing。
  2. 对账命令同时处理 `Failed`（查询原 `out_refund_no`），确认 SUCCESS 则补完成，确认 CLOSED/ABNORMAL 则保持失败。
  3. 补用例：Failed 退款收到 SUCCESS 回调/对账应完成。

### [x] PAY-11 微信商户配置选取不一致；停用配置导致 500 或回调永久失败

- **备注**：FIN-11 部分改善，仍未闭环。
