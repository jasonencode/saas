## 一、P0 —— 资金风险

### [x] RF-01 失败退款「重置申请」后再次发起，可能重复打款

- **文件**：`app/Services/Mall/RefundActions/ReApply.php:35-39`；`app/Policies/Mall/RefundPolicy.php`；`app/Filament/Actions/Mall/ReApplyRefundAction.php`
- **问题**：`ReApply` 允许 `Failed → Pending`，重置后再发起会新建支付退款单（新 `out_refund_no`），若原通道已受理则重复打款。
- **修复**：
  - `ReApply::REAPPLICABLE` 移除 `Failed`，只允许 `Rejected` / `Cancelled`；
  - `RefundPolicy::reApplyRefund()` 与 `ReApplyRefundAction` 可见性同步移除 `Failed`；
  - 失败单统一走 `ReRefund`（复用原支付退款单号，通道侧幂等）；
  - 新增用例：`RefundOperationsTest::test_reapply_failed_refund_is_rejected`。
- **残余**：如后续业务仍需要「失败后重新建单」，必须先通过 `WechatPaymentService::queryRefund()` 核对旧单状态。

## 三、P2 —— 一致性、审计、文档

### [~] RF-08 金额 float 残留

- **已改**：
  - `RefundData::$freightAmount` 改为两位小数字符串（构造时 `number_format` 归一 + `bccomp` 校验）；
  - `RefundService::updateRefundAmount()` / `RefundActions\UpdateAmount` 改字符串金额，内部用 `bccomp` / `bcadd`；
  - `Apply::netUnitPrice()` 改用新增的 `bcRound()`（half up），去掉 `number_format((float) bcdiv(...))`。
- **未改**：`UserAccountService::modifyAsset(float $amount)` 仍是 float 入口（影响面大，需单独重构为分单位或字符串 + 全量调用点迁移）。
- **建议**：下一轮把账户资产服务改为字符串/整数分，并给 `user_account_logs` 补幂等唯一索引。

### [x] RF-09 删除「退款失败」单在策略与动作间不一致

- **决策**：失败单不允许删除（保留资金追溯）。
- **修复**：`Destroy::assertDeletable()` 移除 `Failed`，与 `RefundPolicy::delete()` 对齐；新增用例 `test_destroy_failed_refund_is_rejected`；文档 `docs/development/refund-permissions.md` 增补 4.3 边界表。

### [x] RF-10 历史 `Received` 状态不占用退款额度

- **修复**：
  - `RefundStatus::effectiveCases()` 重新纳入 `Received`（其商品尚未退款，必须继续占用数量与金额）；
  - 单元测试 `RefundStatusTest::test_effective_cases` 同步更新。
- **不做数据迁移**：当前为开发环境、无历史 `received` 数据，不提供状态迁移脚本；若线上出现 `received` 历史单，可手工执行 `UPDATE refunds SET status = 'processing' WHERE status = 'received'` 后继续走「发起退款 / 确认退款」。

### [x] RF-11 处理中退款缺少超时兜底，审核后不会自动发起

- **修复**：`Apply::after()` 在仅退款自动审核通过后自动调用 `Process` 创建支付退款单（存在已支付支付单时），失败只 `report` 不阻断；极速退款仍由队列自行编排。
- **效果**：未命中极速规则的仅退款也会自动进入财务审核，不再依赖商家手动点「发起退款」。
- **用例**：`ExpressRefundTest::test_store_switch_off_keeps_manual_flow` 改为断言自动创建 1 张 `pending` 支付退款单且不自动打款。
- **残余**：售后单长期停留 `processing` 的定时提醒/自动重试未实现，建议后续加每日巡查任务。

### [~] RF-12 退款资源回收需按数量/履约方式确认

- **已改**：`Identity::refund()` 改为按订单项**累计已完成退款数量**判断，只有数量全部退完才撤销身份，部分退款不再提前回收权益。
- **已确认**：`Sku::refund()` 回补库存发生在退款完成时，而退货退款必须先「确认签收」才会完成，因此当前回补时机可接受，无需按验收状态拆分。
- **建议**：如后续需要「待检库存」，再单独扩展库存字段与回补逻辑。

### [x] RF-13 审计日志细节

- **修复**：
  - `RefundService::logPaymentFailure()` 操作人改为队列账号（`System::QUEUE_ID`），不再伪造成用户；
  - `AbstractOperation::dispatch()` 的 `log()` 改为 `try/catch + report`，审计日志异常不再把已提交的业务报成失败。

### [x] RF-14 零散一致性问题

- **修复**：
  - `reason_detail` 统一为 200 字符（`RefundRequest` 校验与提示、`RefundData` 保持一致）；
  - `RefundController::index()` 的 `keyword` 生效：按退款单号 / 订单号模糊搜索；
  - `RefundController::store()/index()/show()` 统一加载 `express.express`，物流公司名称在各接口一致返回；
  - `Complete::allItemsRefunded()` 的 `order_item_id` 比较加 `(int)` 归一。
