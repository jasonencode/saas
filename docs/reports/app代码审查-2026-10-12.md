## 二、事件-监听器接线全图

> 前置结论：本项目 Laravel 13 默认开启事件自动发现（`EventServiceProvider::$shouldDiscoverEvents = true`），
> `app/Listeners/**` 会被**自动注册**，无需手动绑定。因此「监听器文件存在但方法体为空」= 事件会被投递但没有副作用。

### 2.1 接线正常 ✅

| 事件 | 监听器 | 作用 |
|---|---|---|
| `OrderCreated` | `OrderCreatedListener` | 写入 `expired_at` + 投递 `AutoCloseOrder` 延时关单 |
| `OrderPaid` | `GrantIdentityOnOrderPaid` | 调 `IdentityService::grantOnPaid()` 授予身份 |
| `InvoiceApplicationSubmitted` | `SendInvoiceApplicationNotification` | 发票申请通知 |
| Laravel `Login` | `AuthenticatedRecord`、`ClearTenantTokens` | 登录记录 / 清理租户令牌 |
| 调度事件 | `RecordScheduleRunLog`、`RecordManualCommandRun`、`ScheduleListener` | 调度日志 |
| `UserCreatedEvent` | 经 `User` 模型 `$dispatchesEvents` 映射派发 | — |

### 2.2 监听器为空的 7 个订单事件 ⚠️

`app/Listeners/Mall/` 下这 7 个文件的 `handle()` 内只有空的 `try { } catch (Exception) { }`，
**而事件都已在 `OrderService` 中正常 dispatch**：

| 监听器（空实现） | 事件 | 派发位置 |
|---|---|---|
| `OrderCanceledListener` | `OrderCanceled` | `OrderService.php:363`（取消订单） |
| `OrderPaidListener` | `OrderPaid` | `OrderService.php:436`（支付成功） |
| `OrderCompletedListener` | `OrderCompleted` | `OrderService.php:440`、`:739` |
| `OrderDeliveredListener` | `OrderDelivered` | `OrderService.php:503`（发货） |
| `OrderPartiallyShippedListener` | `OrderPartiallyShipped` | `OrderService.php:505`（部分发货） |
| `OrderSignedListener` | `OrderSigned` | `OrderService.php:631`（签收） |
| `OrderPreparingListener` | `OrderPreparing` | `OrderService.php:771`（备货） |

**影响**：订单状态流转的**下游副作用全部未执行**。事件发得出去，接收方什么都没做。

**佐证**：`app/Notifications/Mall/` 下已写好的 `OrderPaidNotification`、`OrderDeliveredNotification`、
`OrderSignedNotification` **全库检索仅被 `MessageSeeder` 引用，从未在任何业务路径中发出** ——
符合「通知本应在这些监听器里发出，但监听器未实现」的判断。

> 注：`OrderPaid` 另有 `GrantIdentityOnOrderPaid` 承担「授予身份」，
> 故 `OrderPaidListener` 空缺只影响通知等其余副作用；其余 6 个事件则完全无副作用。

## 三、潜在错误清单（按建议处理顺序）

### 3.1 高：7 个空监听器 → 订单通知链路静默失效

见 2.2。**建议**：补齐 7 个 `handle()` 实现，将已有通知类接入；短期无法实现的至少改为 `report($e)` 或落日志，
避免「以为发了通知其实没发」的静默状态。

### 3.2 高：静默吞异常，故障不可观测

| 文件 | 行 | 代码 | 影响 |
|---|---|---|---|
| `app/Http/Middleware/ApiRecord.php` | 50 | `} catch (Throwable) {` | API 日志写库失败无痕；另 `parseInput()` 抛 `JsonException` 亦被吞 |
| `app/Jobs/Mall/AutoCloseOrder.php` | 27 | `} catch (Exception $e) {` | **订单自动关闭失败无声无息**，订单永久停留在待支付 |
| 上述 7 个监听器 | — | `} catch (Exception) {` | 同上 |

**建议**：至少 `report($e)`。正确示范见 `OrderCreatedListener`（`catch (Throwable $e) { report($e); }`）。

### 3.3 中：余额校验在事务外 —— 并发可超额扣减

`app/Services/Finance/UserAccountService.php`

```php
// modifyAsset()：第 43 行余额检查在事务之外
if ($amount < 0 && $account->$field + $amount < 0) {
    throw new InvalidArgumentException(...);
}
DB::transaction(static function () use (...) {   // 第 49 行才开事务
    $account->increment($field, $amount);          // 第 53 行
```

| 方法 | 校验行 | 事务行 | 问题 |
|---|---|---|---|
| `modifyAsset()` | 43 | 49 | 校验读的是内存旧快照，扣减靠 `increment`/`decrement`，无行锁 |
| `frozenAsset()` | 105 / 111 | 117 | 同模式 |

**风险**：两个并发请求（如重复提交提现 / 扣款）可同时通过检查，导致余额扣为负数。

**背景**：`WithdrawService` 已在 2026-09-11 加固为「事务内 `lockForUpdate`」，本项目全库仅 3 处行锁；
`UserAccountService` 是**尚未加固的同类入口**。

**建议**：将充足性校验移入 `DB::transaction` 内，先 `lockForUpdate()` 重读账户行再判断。

### 3.4 中：空实现方法 → 调用即 TypeError

`app/Support/Export/UserExport.php:68`

```php
public function toResponse($request): Response
{
    // TODO: Implement toResponse() method.
}
```

声明返回 `Response` 但无 `return`，一旦被调用即 `TypeError`。**建议**：实现或删除该导出类。

### 3.5 低：`first()` 后直接访问属性（潜在 NPE）

| 文件 | 行 | 代码 |
|---|---|---|
| `app/Http/Resources/Mall/CartResource.php` | 34 | `$storeItems->first()->product->storeConfigure` |
| `app/Services/Campaign/CouponService.php` | 346 | `$items->first()->tenantId` |
| `app/Console/Commands/Seeders/OrderSeeder.php` | 118 | `$orderItems->first()->tenantId` |

集合为空时抛 `Error: Call to a member function on null`。**建议**：加空判断或改用 `firstOrFail()` / `?->`。

### 3.6 低：调试残留与风格

| 文件 | 情况 | 处置 |
|---|---|---|
| `app/Console/Commands/Test/Test.php:19` | `dump(Sku::first()->name)` | 该目录已被 `.gitignore`（`/app/Console/Commands/Test/*.php`）排除，不影响仓库；建议本地清理 |
| `app/Http/Middleware/ApiRecord.php` | Pint 报风格问题 | 跑 `vendor/bin/pint` 即可 |
| `config/filesystems.php` | Pint 报风格问题 | 同上（不在 `app/` 范围内，一并记录） |

### 3.7 观察项：全库无 `declare(strict_types=1)`

1350 个文件**统一未声明**严格类型。属项目统一风格而非缺陷，但意味着隐式类型转换在所有边界生效
（如 `"1.5"` → `1.5`、`1` → `true`）。如需收紧可分批引入，属长期议题。

## 附：本次审查确认的事实修正

审查过程中曾出现两处需修正的初步判断，已核实并更正，记录以防误导：

1. **监听器是否注册** —— 初步怀疑「无 `EventServiceProvider` 故监听器未注册」；
   核实 Laravel 13 默认 `$shouldDiscoverEvents = true`，**监听器会被自动注册**，问题在于方法体为空而非未绑定。
2. **`UserCreatedEvent` 是否为死事件** —— 初步检索 `::dispatch` 零命中；
   核实其通过 `User` 模型 `$dispatchesEvents`（`app/Models/User/User.php:34`）映射派发，**接线正常**。
