## 二、A 类：环境配置缺失（17 条）

根因：项目根目录缺 `.env`，`APP_KEY` 与 `AES` 密钥为空。这批失败是**同一个原因的不同表现**，不是代码缺陷。

| 测试文件 | 失败数 | 错误信息 | 具体表现 |
|---|---|---|---|
| `Tests\Feature\ExampleTest` | 1 | `MissingAppKeyException: No application encryption key has been specified` | 应用启动即中断 |
| `Tests\Feature\System\ScheduleRunLogPanelTest` | 6 | `ViewException: No application encryption key has been specified` | 渲染Blade 视图时中断 |
| `Tests\Feature\User\RealnameApiTest` | 4 | `RuntimeException: 未配置AES密钥` (`app/Support/AES/AES.php:105`) | 实名认证接口链路中断 |
| `Tests\Feature\User\RealnameServiceTest` | 6 | `RuntimeException: 未配置AES密钥` (`app/Support/AES/AES.php:105`) | 实名服务中断 |

**验证方式**：
```bash
php artisan test tests/Feature/User/RealnameServiceTest.php --display-warnings
```
warning 中可见 `file_get_contents(.../.env): Failed to open stream: No such file or directory`

**修复方向**：复制 `.env.example` 为 `.env`，执行 `php artisan key:generate`，并补 `AES` 密钥配置。

## 三、C 类：工厂未填必填列（30 条，最大头）

根因：`ContentFactory` 未给 `contents.category_id` 赋值，而迁移中该列为 `NOT NULL` 无默认值。所有创建 content 的测试在 `setUp` 阶段就崩溃，连带整个测试类全部失败。

| 测试文件 | 失败数 | 错误信息 |
|---|---|---|
| `Tests\Feature\Content\CommentApiTest` | 19 | `QueryException: SQLSTATE[23000] NOT NULL constraint failed: contents.category_id` |
| `Tests\Feature\Content\ContentApiTest` | 11 | 同上 |

**失效机制**：
```
SQLSTATE[23000]: Integrity constraint violation: 19 NOT NULL constraint failed:
contents.category_id (SQL: insert into "contents" ...)
```

**关键点**：这是**单点根因放大成 30 条失败**——一个 `category_id` 缺失导致 30 个用例无法执行。修复工厂默认值，这 30 条大概率一次性全绿。

**修复方向**：检查 `database/factories/Content/ContentFactory.php` 是否遗漏 `category_id`，或为该列补默认值/设为 nullable。

### E 类：响应结构与断言不匹配（2 条）

| 测试文件 | 失败用例 | 错误信息 | 说明 |
|---|---|---|---|
| `Tests\Feature\TenantMallConfigurePageTest` | `it hydrate…` | `TypeError: assertArrayHasKey() 参数 #2 必须为 array，传入 null`（第 24 行） | Livewire::test() 拿到的 `data` 为 null |
| `Tests\Feature\TenantMallConfigurePageTest` | `it de…` | `ErrorException: Attempt to read property "form" on null`（第 34 行） | `Livewire::test()->instance()` 返回 null |

## 五、G 类：本次改动引入的回归（4 条，**已修复**）

**这是唯一由本次修复引入的失败，必须处理。**

背景：本次为修复「业务异常统一返回 500」，在 `ApiExceptionHandler` 中新增了 `RuntimeException` / `InvalidArgumentException` → **400** 的映射。这些测试的断言仍写的是**旧的 500**。

| 测试文件 | 失败用例 | 异常 | 现返回 |
|---|---|---|---|
| `Tests\Feature\User\InvoiceApiTest` | `apply invoice rejects order o…` | `RuntimeException: 只能为自己的订单申请开票` (`InvoiceService.php:137`) | 400 |
| `Tests\Feature\User\InvoiceApiTest` | `apply invoice rejects canceled…` | `RuntimeException: 订单未支付或已取消，不可开票` (`InvoiceService.php:142`) | 400 |
| `Tests\Feature\User\InvoiceApiTest` | `apply invoice rejects order a…` | `RuntimeException: 订单已申请过开票` (`InvoiceService.php:165`) | 400 |
| `Tests\Feature\User\SafeApiTest` | `change payment password fails wi…` | `InvalidArgumentException: 原支付密码不正确` (`UserAccountService.php:243`) | 400 |

**归因验证**（严格确认非既有失败）：
```bash
git stash push -m "verify"        #暂存本次改动
php artisan test --compact tests/Feature/User/InvoiceApiTest.php tests/Feature/User/SafeApiTest.php
# → Tests: 32 warnings (125 assertions)   零失败
git stash pop                      # 恢复改动
```

**处理方式**：采用方案A——将测试断言由 `500` 改为 `400`。理由：这些异常（"只能为自己的订单申请开票"、"原支付密码不正确"）本质就是可预期的用户输入错误，400 比 500 更符合语义，也与本次异常映射的整改目标一致。**未回退异常映射**。

**修复结果**：`InvoiceApiTest` 与 `SafeApiTest` 共 32 个用例全部通过，全项目失败数 71 → 67。全项目已无任何 `assertStatus(500)` 断言残留（已 grep 确认）。

| 位置 | 改动 |
|---|---|
| `tests/Feature/User/InvoiceApiTest.php` | 3 处 `assertStatus(500)` → `assertStatus(400)` |
| `tests/Feature/User/SafeApiTest.php` | 1 处 `assertStatus(500)` + `assertJsonPath('code', 500)` → 400 |
