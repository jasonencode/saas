## 一、总体结论

1. **架构骨架是好的**：`OrderService` 门面 + 每状态一个 Action，`before → handle（自带事务）→ log → afterCommit` 分层清晰；`pay / cancel / deliver / sign / complete` 都做了 `lockForUpdate` 或 `assertCanWithLock` 的锁内状态复核，`Sku::deductStock` 用 `where stock >= qty` 的条件更新，优惠券核销用 `where is_used = false` 的乐观更新——**主流程的并发处理明显强于一般项目**。
2. **订单链路仍有 4 个断点**：后台代付不产生支付单（订单永久无法退款）、发货没有「已发数量」概念（部分退款后超发或永久卡在 PartiallyShipped）、后台删除绕过领域服务（库存/券不释放、强删产生孤儿）、订单详情页因类型未导入必 500。
3. **状态机有一条死路**：`PartiallyShipped → Signed` 被允许，用户在只收到部分商品时就能签收，剩余明细之后**再也没有发货入口**。
4. **服务层缺少租户断言**：Filament 5 会给资源模型注册模型级租户作用域，所以后台页面「看起来」是隔离的；但 `Verify / Deliver / Sign / Complete` 本身不校验 `tenant_id`，一旦被命令、队列或 API 复用即跨租户。
5. **金额口径基本统一为字符串 + bcmath**（`getTotalAmount()`、`OrderItemDto::getAmount()`、`OrderItem::getSubTotalAttribute()` 均返回 string），缺口集中在三个地方：`updateFreight(float)`、`Order::@property float $total_amount` 注释、以及「改运费后不同步支付单金额」导致微信按旧金额收款。

**统计：严重 4 / 高 8 / 中 14 / 低 2（共 28 条）。**

## 二、订单主链路与断点

```
创建 Create / CreateOrder
  ├─ OrderItemDto 构造时调用 checkOrderable（商品上下架 + 库存）
  ├─ 事务内：建单 → 建明细 → Ordered 型扣库存 → 用券 → 落地址快照 → syncWithoutDetaching(user_tenant)
  ├─ ✗ 购物车入口不强制邮寄地址（ORD-05）
  ├─ ✗ 不校验店铺是否开通 / 租户是否可用（ORD-22）
  ├─ ✗ 不校验「商品是否在该自提点可自提」（ORD-19 关联项，见 ORD-22 说明）
  └─ 派发 OrderCreated → 监听器延迟投递 AutoCloseOrder（无扫描补偿，ORD-16）

支付 Pay
  ├─ 事务内：行锁 → 状态校验 → Paid 型扣库存 → 置 Paid/PickupPending/Completed
  ├─ ✗ 通知在事务内（tenant 为 null 时直接 500 且回滚已支付）（ORD-07）
  ├─ ✗ SKU 软删后 $item->orderable 为 null，扣库存被静默跳过 → 超卖（ORD-08）
  └─ 派发 OrderPaid / OrderCompleted

备货 Preparing（仅状态）

发货 Deliver / CancelDeliver
  ├─ ✗ order_items 没有 shipped_qty，只靠 order_shipping_id 整行绑定（ORD-02）
  ├─ ✗ 完成判定用「明细行数」，全退明细永远拉低分子 → 永久 PartiallyShipped
  ├─ ✗ express_id / express_no 无服务层校验（ORD-18）
  └─ ✗ 删除发货记录回退状态时不清 auto_sign_at，仍用行数判定（ORD-19）

签收 Sign / DelaySign
  ├─ ✗ PartiallyShipped 可直接 Signed → 剩余明细永久无法发货（ORD-06）
  └─ 自动签收命令只扫 Delivered（不会扫 PartiallyShipped）

完成 Complete（定时 OrderAutoCompleteCommand）
  └─ ✗ chunk() 边改状态 → 跳单；失败仍返回 SUCCESS（ORD-15）

取消/删除 Cancel / Delete
  ├─ 服务内释放库存/券/秒杀名额（Delete 仅 Pending 才释放，避免重复回补）
  └─ ✗ 后台默认 DeleteAction / ForceDeleteBulkAction 完全绕过服务（ORD-03）
```

## 三、严重问题

### ORD-01 ｜ 严重 ｜ 资金断链

**后台「订单付款」扣余额却不创建支付单，该订单永久无法退款**

- **位置**：`app/Filament/Actions/Mall/OrderPaymentAction.php:84-112`、`app/Services/Mall/RefundActions/Process.php:108-116`、`app/Http/Controllers/Finance/PaymentController.php:74`
- **代码要点**：Action 在事务内只做 `UserAccountService::modifyAsset(..., -totalAmount)` 再 `OrderService::pay()`；全仓库 `PaymentOrder::create` 仅出现在 `PaymentController:74`（另一处 `app/Console/Commands/Test/OrderFlowVerify.php` 属测试命令）。
- **失败场景**：商家在后台替用户用余额付款 → 余额已扣、订单已 Paid。用户随后申请售后，`Process` 里 `$order->paymentOrders()->where('status', Paid)...->first()` 为空 → 抛「没有可退款的支付单」；自提超时退款、商家代退款、极速退款全部打不了款，财务也没有支付单可对账。
- **修复建议**：改为复用 `PaymentService`（先按 `PaymentableResolver::amountOf` 建 `PaymentOrder`，再 `payByBalance`），或在本 Action 事务内补建一条 Paid 支付单后再 `pay()`；补「代付后全额退款」用例。

### ORD-02 ｜ 严重 ｜ 发货数量口径

**没有「已发数量」字段：部分退款后 API 超发，后台整行剔除导致订单永久「部分发货」**

- **位置**：`app/Services/Mall/OrderActions/Deliver.php:77,97-102`、`app/Models/Mall/OrderItem.php:100-113`、`app/Filament/Actions/Mall/OrderShipAction.php:88,152-161`、迁移 `database/migrations/0003_02_00_000001_create_orders_table.php:95-140`
- **代码要点**：`order_items` 只有 `order_shipping_id`（整行绑定），没有 `shipped_qty`；`getShippableQtyAttribute()` 直接返回 `getMaxRefundCounts()`（= `qty - 已退`），与已发数量无关；完成判定为
  ```php
  $totalItems   = $this->order->items()->count();
  $shippedItems = $this->order->items()->whereNotNull('order_shipping_id')->count();
  ```
  UI 侧 `default()` 用 `reject(fn ($item) => $item->getMaxRefundCounts() < $item->qty)` 整行剔除，`hasUnshippedItems()` 也要求 `getMaxRefundCounts() >= qty`。
- **失败场景**：
  1. 明细 `qty=5`、已退 2 → 服务仍按整行发 5 件，**多发 2 件**（`getShippableQtyAttribute() > 0` 只拦「全退」）。
  2. 后台发货弹窗把该行剔除，剩余 3 件**永远发不出去**。
  3. 全退明细的 `order_shipping_id` 永远为 null，`shippedItems` 恒小于 `totalItems` → 订单永远停在 `PartiallyShipped`，`auto_sign_at` 不写入，自动签收/自动完成链路整体失效。
- **修复建议**：`order_items` 增加 `shipped_qty`（或独立 `order_shipping_items` 记数量）；可发 = `qty - refunded_qty - shipped_qty`；完成/部分发货判定改为数量口径，UI 与服务共用同一函数；补「部分退款后发货」「全退一行 + 发剩余」两条用例。

### ORD-03 ｜ 严重 ｜ 后台绕过领域服务

**订单删除 / 批量删除 / 永久删除绕过 `OrderService`，资源不释放、数据可物理抹除**

- **位置**：`app/Filament/Tenant/Clusters/Mall/Resources/Orders/Tables/OrdersTable.php:130-131,135-140`、`app/Filament/Tenant/Clusters/Mall/Resources/Orders/Pages/ViewOrder.php:54-55`；对照 `app/Services/Mall/OrderActions/Delete.php:52-58`
- **代码要点**：表格与详情页使用 Filament 原生 `DeleteAction`（等价 `$record->delete()`）、`DeleteBulkAction`、`ForceDeleteBulkAction`、`RestoreBulkAction`，且都没有 `visible()`/`userCan()`；服务里才有「Pending 状态先 `releaseOrderResources()`（回补库存、释放券、释放秒杀名额）再删除」；`Order` 的 `boot()` 只注册了 `creating`（写 `expired_at`），**没有 `deleting` 钩子**。
- **失败场景**：删除一笔待付款订单（`DeductStockType::Ordered` 商品已在下单时扣库存）→ 库存不回补、已核销优惠券不释放、秒杀名额不归还；`ForceDeleteBulkAction` 还会把 `order_items`、`order_shippings`、`refunds`、`payment_orders.paymentable`、`event_logs` 变成孤儿（这些关联基本无外键），售后与财务对账不可恢复。
- **修复建议**：删除统一改为 `->action(fn ($record) => service(OrderService::class)->delete(...))`；移除 `ForceDeleteBulkAction`（或限制为系统角色 + 二次确认 + 审计）；`Order::deleting` 统一做一次幂等释放兜底。

### ORD-04 ｜ 严重 ｜ 运行时错误

**两个面板的 `OrderInfolist` 使用了未导入的 `Order`，打开订单详情必 500**

- **位置**：`app/Filament/Backend/Clusters/Mall/Resources/Orders/Schemas/OrderInfolist.php:79`、`app/Filament/Tenant/Clusters/Mall/Resources/Orders/Schemas/OrderInfolist.php:74`
- **代码要点**：`->visible(fn (Order $record): bool => bccomp((string) $record->coupon_discount, '0', 2) === 1)`；两个文件顶部只导入了 `FulfillmentType / UserEntry / Infolists / Schemas / TextSize`，**没有 `use App\Models\Mall\Order;`**（已 grep 确认两文件均无该 use）。
- **失败场景**：闭包类型解析到不存在的 `...\Schemas\Order`，传入真实模型触发 `TypeError`：任意运营或租户人员打开「订单详情」即 500；由于测试没有订单详情页用例，1285 条绿灯未能发现。
- **修复建议**：两处补 `use App\Models\Mall\Order;`；补 `ViewOrder` 渲染用例。

## 四、高优先级问题

### ORD-05 ｜ 高 ｜ 入参校验

**购物车下单入口不强制邮寄地址，可建出「没有收货信息」的快递订单**

- **位置**：`app/Http/Requests/Mall/OrderFromCartRequest.php:33-36`、`app/Services/Mall/OrderActions/CreateOrder.php:94-100,160-164`、`app/Services/Mall/OrderActions/Deliver.php:89-91`
- **代码要点**：`OrderFromCartRequest` 的 `address_id` 只有 `nullable` + `OrderAddressRule`，**没有** `Rule::requiredIf(mail)`；对比 `OrderRequest.php:35-39`（直购下单）是有的。`CreateOrder` 只在 `if ($address)` 时写 `order_addresses`；`Deliver` 也在 `if ($this->order->address)` 时才 `setAddress()`。
- **失败场景**：`POST /api/mall/cart/checkout` 传 `fulfillment_type=mail` 不带 `address_id` → 建出无 `order_addresses` 的快递单；付款后发货记录没有收件人/手机号/地址，仓库无法出库；`ModifyAddress` 又因 `address = null` 抛「订单收货信息不存在」，而该入口当前根本没挂到界面（ORD-20），只能靠人工改库。
- **修复建议**：`OrderFromCartRequest` 补 `Rule::requiredIf(fn () => $this->string('fulfillment_type') === FulfillmentType::Mail->value)`；并在 `CreateOrder::before()` 对 `FulfillmentType::Mail` 断言地址非空（服务层兜底）。

### ORD-06 ｜ 高 ｜ 状态机

**`PartiallyShipped` 可直接签收，剩余未发明细永久无法发货**

- **位置**：`app/Enums/Mall/OrderStatus.php:184`、`app/Services/Mall/OrderActions/Sign.php:46-58`、`app/Services/Mall/OrderActions/Deliver.php:43-46`
- **代码要点**：`self::PartiallyShipped => [self::Delivered, self::Signed]`；`Sign::handle()` 只做 `assertCanWithLock(..., Signed)`，不检查是否还有未发/未退完的明细；而 `Deliver::before()` 要求当前状态 ∈ `Paid/Preparing/PartiallyShipped`。
- **失败场景**：一笔两行订单只发了 A 行 → 状态 `PartiallyShipped`；用户（或后台）点「确认收货」→ 状态 `Signed`，随后自动完成。B 行永远无法再发货，也无法进入退货流程（退货基于已发记录），用户付了钱拿不到货。
- **修复建议**：`PartiallyShipped → Signed` 仅在「无剩余可发明细」时允许，或在 `Sign` 内断言 `shipped_qty + refunded_qty >= qty`；否则只允许 `PartiallyShipped → Delivered`。

### ORD-07 ｜ 高 ｜ 事务副作用

**支付成功在事务内直接 `tenant->notify()`；租户为空或通知异常会回滚整笔已支付**

- **位置**：`app/Services/Mall/OrderActions/Pay.php:93-100`
- **代码要点**：
  ```php
  $this->order->save();
  $this->order->tenant->notify(new NewOrderToTenant($this->order));   // 事务内、无 try/catch
  OrderPaid::dispatch($this->order, $this->user);                      // ShouldDispatchAfterCommit，安全
  if ($targetStatus === OrderStatus::Completed) { OrderCompleted::dispatch(...); }
  ```
  `orders.tenant_id` 可空（`Blueprint::tenant()` 宏 nullable），`tenant()` 是普通 `belongsTo`，无 `withDefault()`。
- **失败场景**：① 订单 `tenant_id` 为 null（历史数据/无租户下单）→ `notify` on null → `Error` → 事务回滚，余额已扣/渠道已收款的支付被撤销；② 通知通道异常（邮件配置错误、`notifications` 表写入失败、路由名变更）同样回滚订单状态、库存扣减与调用方事务里的 `PaymentOrder`，渠道侧已收款只能人工对账。
- **修复建议**：通知移入 `DB::afterCommit()` 并 `try/catch + report()`；对 `tenant` 为 null 显式跳过。事件类监听器已经这么做了（`OrderPaidListener`），此处遗漏。

### ORD-08 ｜ 高 ｜ 库存一致性

**库存扣减/回补依赖「当前」商品配置与关联是否存在，SKU 软删后静默跳过**

- **位置**：`app/Services/Mall/OrderActions/Pay.php:71`、`app/Services/Mall/OrderActions/Concerns/ReleasesOrderResources.php:31-41`、`app/Models/Mall/Sku.php:105-116,147-157`
- **代码要点**：`Pay` 里 `if ($orderable && $orderable->getDeductStockType() === DeductStockType::Paid) { ... }`；`ReleasesOrderResources` 同样 `if ($orderable && ...)`；`orderable` 是 `morphTo`，默认排除软删的 `Sku`，于是 `$orderable === null` 时**直接跳过**；`getDeductStockType()` 读的是 `$this->product->deduct_stock_type`（下单时的配置没有快照）。
- **失败场景**：① 用户下单（Paid 型扣库存）后商家删除 SKU → 支付成功时 `orderable` 为 null，库存不扣 → 超卖；② 商品配置从 `Ordered` 改为 `Paid` 后再取消订单：下单时已扣库存，取消时按新配置判断为 `Paid` → 不回补，库存永久少一份；③ 从 `Paid` 改 `Ordered` 则可能重复回补（虚增）。
- **修复建议**：在 `order_items` 快照下单时的 `deduct_stock_type`（与 ORDER-02 的 `shipped_qty` 一起加），扣减/回补一律按快照；`orderable` 用 `withTrashed()` 或回退到 `orderable_id` 直接更新 `skus`；有未完成订单的 SKU 不允许物理删除（改为下架）。

### ORD-09 ｜ 高 ｜ 授权 / 运行时错误

**核销页 `canAccess()` 把类名字符串传给强类型策略，非系统角色打开即 500**

- **位置**：`app/Filament/Tenant/Clusters/Mall/Pages/PickupVerify.php:70-73`、`app/Policies/Mall/OrderPolicy.php:203-210`
- **代码要点**：`return MallCluster::isAvailable() && userCan('orderVerify', Order::class);`，而策略签名是 `orderVerify(Authenticatable $user, Order $order)`。
- **失败场景**：Gate 以字符串调用策略 → `TypeError`。只有 `Policy::before()` 命中（`isAdministrator()`，即主键 1 或 `is_sys` 角色）才会提前 `return true`；**租户自建角色的普通员工访问「核销」页直接 500**，自提核销对这类账号完全不可用，而超管永远看不到这个问题。
- **修复建议**：拆出无实例的 `orderVerifyAny(Authenticatable $user): bool` 供页面准入使用，或传 `new Order`；补「租户普通角色可打开核销页」用例。

### ORD-10 ｜ 高 ｜ 空指针 / 售后

**SKU/商品软删后订单详情与「代用户退款」弹窗 500**

- **位置**：`app/Http/Resources/Mall/OrderItemResource.php:36-49`、`app/Filament/Actions/Mall/CreateRefundAction.php:202`
- **代码要点**：`formatOrderable()` 直接 `$orderable->getMorphClass()/getOrderableName()`，无 `?->`；对比 `RefundActions/Apply::assertRefundItems` 已用 `?->` 兜底，口径不一致。
- **失败场景**：商家下架并删除 SKU（很常见）→ `GET /api/mall/orders`、`/orders/{no}`、`/orders/{no}/shipping` 以及后台代退款弹窗全部「Call to a member function on null」，售后被阻断。
- **修复建议**：统一 `$orderable?->` 并回退到 `order_items.orderable_name/orderable_type` 快照；补「软删 SKU 的订单详情/代退款」用例。

### ORD-11 ｜ 高 ｜ 资金快照

**改运费不联动已创建的待支付支付单，微信按旧金额收款且无人校验差额**

- **位置**：`app/Services/Mall/OrderActions/UpdateFreight.php:70-80`、`app/Http/Controllers/Finance/PaymentController.php:205-212`、`app/Services/Finance/PaymentService.php:69-87,213-221`
- **代码要点**：`UpdateFreight` 只写 `orders.freight`；`payWechat()` 用 `(int) bcmul($payment->amount, '100', 0)`（支付单创建时的快照金额）；只有余额支付会在事务内 `payableAmount()` 重算并回写（`PaymentService:69,87`），`markPaidWithBusiness` 不比对实付与应付。
- **失败场景**：用户先 `POST /api/payments` 建支付单（88 商品 + 10 运费 = 98），商家随后把运费改成 30（订单应付 118），用户再扫码 → 微信只收 98；回调只校验 `out_trade_no`，订单照样置 Paid，少收 20 元且对账不平。反向（运费调低）则多收钱，需要人工退款。
- **修复建议**：改运费时同步把该订单 `status=Pending` 的 `PaymentOrder.amount` 更新为 `getTotalAmount()`（或作废旧支付单要求重建）；`payWechat` 前用 `payableAmount()` 复核，不一致直接拒绝并提示刷新。

### ORD-12 ｜ 高 ｜ 授权口径

**`OrderPolicy::delete`、服务 `Delete`、表格 `visible()` 是三套口径**

### 7.2 本轮纠正的两条旧判断

1. **「`Sku::checkOrderable()` 存在但从未被调用」→ 不成立。**
   `OrderItemDto::__construct()` 默认 `check: true`，会执行 `if ($check && $reason = $orderable->checkOrderable($qty))`，所以下单链路确实会做上下架与库存校验。真实问题是实现本身不安全（父商品软删时空指针、不校验店铺状态），见 ORD-25。

2. **「无收货地址订单（虚拟/自提）详情 500」→ 不成立（MALL-27 误报）。**
   Laravel 13 的 `Illuminate\Http\Resources\ConditionallyLoadsAttributes::filter()` 中有：
   ```php
   if ($value instanceof self && is_null($value->resource)) {
       $data[$key] = null;
   }
   ```
   `OrderAddressResource::make(null)` 作为 `address` 键的嵌套 Resource，会在 `filter()` 阶段被直接置为 `null`，**不会执行 `toArray()`**，因此不会空指针。`OrderLifecycleApiTest` 里虚拟单（无地址）`show` 断言 200 也印证了这一点。
   需要注意的是：同文件里的 `'user' => UserProfileResource::make($this->resource->user)` 同理安全；但 `OrderItemResource` 内部对 `orderable` 的访问是**普通方法调用**，不受该机制保护，所以 ORD-10 依然成立。

## 八、建议回归测试清单

按「一个用例能挡住一类回归」排序，建议补在 `tests/Feature/Mall/`：

1. **后台代付可退款**：`OrderPaymentAction` 代付后断言存在 `payment_orders.status=paid`，且 `RefundService` 能成功创建支付退款单（ORD-01）。
2. **部分退款后发货**：`qty=5` + 已退 2 → 只允许发 3 件，发完后订单进入 `Delivered` 并写 `auto_sign_at`（ORD-02，需先落 `shipped_qty`）。
3. **全退行的完成判定**：3 行明细其中 1 行全退 → 发完另 2 行后必须 `Delivered`，不得卡 `PartiallyShipped`（ORD-02）。
4. **部分发货后签收**：`PartiallyShipped` 且仍有未发明细时 `sign` 应被拒绝（ORD-06）。
5. **购物车 mail 无地址**：`POST /api/mall/cart/checkout` 不带 `address_id` 应 422（ORD-05）。
6. **支付通知失败不回滚**：mock 通知抛异常 → 订单仍 `Paid`、`payment_orders` 仍 `Paid`（ORD-07）。
7. **软删 SKU**：删除 SKU 后订单详情与代退款弹窗仍可渲染/使用（ORD-10、ORD-25）。
8. **改运费后微信金额**：建支付单 → 改运费 → `payWechat` 应拒绝或使用新金额（ORD-11）。
9. **自动完成不跳单**：造 250 笔 `Signed` 订单，跑一次命令后全部 `Completed` 且返回 `SUCCESS`（ORD-15）。
10. **订单详情页渲染**：`ViewOrder` 用有券/无券、有地址/无地址订单各渲染一次（ORD-04）。

## 九、修复优先级

| 优先级 | 条目 | 理由 |
|---|---|---|
| **P0（本周）** | ORD-01、ORD-02、ORD-03、ORD-04 | 资金断链、超发/卡单、数据不可恢复、详情页必 500 |
| **P1** | ORD-05、ORD-06、ORD-07、ORD-08、ORD-09、ORD-10、ORD-11 | 无收货信息订单、状态机死路、支付回滚、超卖、核销不可用、少收款 |
| **P2** | ORD-12、ORD-13、ORD-18、ORD-20、ORD-22、ORD-23 | 口径不一致、租户断言、运单校验、后台能力缺口、业务约束、可退额度 |
| **P3** | ORD-14、ORD-15、ORD-16、ORD-17、ORD-19、ORD-21、ORD-24、ORD-25、ORD-26、ORD-27、ORD-28 | 入参、定时任务、可靠性、金额类型、脏字段、绕过服务、性能、空指针、日志、审计字段 |

> 建议把 ORD-02（`shipped_qty`）、ORD-06（签收前置校验）、ORD-19（删除发货记录）放在同一次改动里做：三者共用「数量口径」这一个新概念，分开改容易再对不齐。
