## 三、跨模块共性问题

### 3.1 授权仍有三条「静默放行」路径

- 租户资源覆写 `canAccess()` 只判断模块开关，绕过 `viewAny`（37/39 个资源，SYS-02 / BE-02）。
- `->strictAuthorization(false)`：策略缺方法默认放行；`forceDelete` 等 ability 未补策略（SYS-03）。
- `AuthorizesModelAccess` 对 null 用户放行（INF-04 / USER-08 / MALL-09）。
- `isAdministrator()` 把「主键=1」和「租户 `is_sys` 角色」都当平台超管（SYS-01）。

**建议**：`canAccess()` 统一改为 `parent::canAccess() && 模块判断`；开启 `strictAuthorization(true)` + CI 校验「每个 Resource 的每个 ability 都有策略」；`before()` 只认平台超管。

### 3.2 租户隔离「非全局」，每个入口都要显式过滤

- `BelongsToTenant` 只提供 `ofTenant()`，不是全局作用域；Filament 5 会给「资源模型」注册模型级作用域，但**服务层、API、Console、非资源模型不受保护**。
- 本期因此仍存在：Content API（CONT-01）、公共自提点/退货地址（MALL-05）、Finance 租户看板与充值单（FIN-01/25）、Campaign 统计与红包打款（CAMP-03/08）、`single_pages.slug`（CONT-02）。

**建议**：抽统一 `TenantContext`（解析 `X-Tenant-Id` 并校验用户归属）；API 层默认注入；`ofTenant(null)` 直接拒绝。

### 3.3 「写而未用」的能力仍比缺失更危险

| 能力 | 位置 | 风险 |
|---|---|---|
| IP 黑名单中间件 | `BlackIpList`（`bootstrap/app.php:44` 注释） | 后台可配置但完全不生效，且实现会先执行业务 |
| API 日志 | `ApiRecord` | 已实现脱敏但未挂载，`api_logs` 永远为空 |
| 访问令牌认证 | `AccessTokenAuthenticate` | 未注册；租户令牌 base64 后无消费端 |
| 商城开通校验 | `EnsureStoreIsOpened` | 别名注册但无路由使用，关店仍可下单 |
| 浏览量去重 | `TrackVisitService` | `views` 可任意刷 |
| 结算凭据 | `VoucherService::create` | 无调用方，且后台建单不派发 Job |
| 支付宝 | `AlipayService` + `getConfig()` 返回 `[]` | 后台可配置，前台无入口且必然报错 |
| RSA 长文本 | `Support/RSA` | 分块尺寸算错，且无调用方 |
| 身份购买 | `IdentityService::purchase` | `is_unique` 语义未完整实现 |

**建议**：逐项决策「启用并补齐安全措施」或「删除」，不要把半成品留在主链路上。

### 3.4 异常分层与错误信息

- `RuntimeException` 仍统一映射 400 + 原始 message（INF-05）；`PDOException/QueryException` 已按 500。
- 多个控制器 `catch (Throwable) { return ApiResponse::error($e->getMessage()); }`（实名、推荐关系等）。
- 新增上传/实名链路本身有 `catch (Throwable)` 直出问题（USER-14）。

**建议**：定义 `BusinessException`（400/422）与系统异常（500 + `report()`）两套出口；禁止控制器直出 `getMessage()`。

### 3.5 金额、并发与幂等

- 金额已大量改为 bcmath 字符串（MALL-24 已修），但红包 Job 仍用浮点 ×100（CAMP-07）。
- 已做好：支付单行锁、退款条件更新、提现锁内校验、红包领取条件更新。
- 仍缺：充值完成无锁（FIN-04）、支付密码无失败计数（FIN-05）、红包 Job 无幂等（CAMP-01）、身份编号 `max+1`（USER-10）、购物车 `firstOrCreate`（MALL-18）。

### 3.6 后台 UI 与领域服务脱节

- Filament 默认删除/批量删除绕过 `OrderService`（MALL-06）、批量审核绕过 `ProductService`（BE-06）、红包码直接改金额（BE-08）。
- 资金/实名/审计类数据可删除或强制删除（BE-05/07、FIN-03/15/26）。
- 运营端订单全流程无入口（BE-12），Campaign 三张核心表无详情入口（CAMP-04）。

**建议**：所有「有副作用的动作」统一调用领域 Service；资金/审计记录只允许「作废」不允许删除。

## 六、已知的「非缺陷」设计取舍

以下事项看起来像问题，但属于有意设计，建议在文档中固化：

1. `ApiResponse::success()` 不包 `data` 层。
2. `BaseCollection` 使用 `list`/`page` 而不是 Laravel 默认 `data`/`meta`。
3. `#[Unguarded]` + 表单层白名单（风险在表单遗漏，不在机制本身）。
4. `->strictAuthorization(false)` + 「每个资源必须补策略」的团队约定（当前漏洞来自约定未被执行）。
5. 计划任务全部 `->onOneServer()`（生产要求 Redis 缓存锁）。
6. 金额列 `unsigned`，不允许负值写入。
