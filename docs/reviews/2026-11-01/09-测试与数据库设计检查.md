## 三、测试体系问题

### T-01 ｜ 高 ｜ 没有 CI，也没有静态分析
- `composer.json` 只有 `test` 脚本（`config:clear` + `artisan test`），没有 PHPStan/Larastan/Psalm，没有 `.github/workflows`（`.github` 已被 `.gitignore`）。
- 影响：类型错误（如 Finance 的 `TypeError`、`Attempt to read property on null`）只能靠运行期发现；「17 失败」无人守门。
- 建议：至少加一个 `composer lint`（Pint `--test`）+ `composer analyse`（Larastan level 5 起步）+ CI 工作流；先把失败用例清零或标记 `markTestSkipped` 并建 issue，保证基线为绿。

### T-02 ｜ 中 ｜ SQLite 测试与 PostgreSQL 生产不一致
- AGENTS 已注明：`AppVersionController` 用 `split_part`，`ProductScopes::ofFilter('freeShip')` 用 `jsonb @> '::jsonb'`，这些在 SQLite 下不可执行或语义不同。
- 影响：最需要回归的查询路径在 CI 中根本没被验证；本次全量测试也没有覆盖到 `freeShip` 分支。
- 建议：关键 SQL 用 PostgreSQL 跑一套集成测试（Testcontainers 或 CI service），或至少给 PG 专用分支加 `@requires` 标记并在 PG job 中执行。

### T-03 ｜ 中 ｜ 工厂数据不完整，默认值与业务预期相反
- 例：`DeliveryRuleFactory` 缺 `status`；`Delivery` 的 `status` 依赖 `easyStatus()` 默认 `false`；`UserFactory` 缺 `tenant_id`（表本身也没有）。
- 影响：测试通过/失败取决于「工厂是否恰好补齐了必填列」，而不是业务逻辑；本次 5 条 Delivery 失败即由此产生。
- 建议：工厂按「业务可用」补全必填字段（`status = true` 等），并对关键默认值写专门用例。

### T-04 ｜ 中 ｜ 大量「枚举 getLabel」测试价值偏低
- `tests/Unit/Enums/**` 有 40+ 文件，大多只断言 `getLabel()` 文本。
- 影响：维护成本高于收益，且文案一改就红一片。
- 建议：保留有 `tryFrom/parseLabel/业务方法` 的枚举测试，纯 label 断言可合并为数据驱动的一条用例。

### T-05 ｜ 低 ｜ 缺少针对性回归用例
各模块报告已列出高风险路径的测试缺口（越权、并发、软删、租户隔离），这里不重复。建议按「先写失败用例 → 再修」的方式补齐。

## 四、数据库设计检查

### 4.1 结构概览

- 45 个迁移文件，创建约 85 张表；迁移命名统一为 `000x_xx_xx_xxxxxx_create_xxx`，但存在同前缀冲突（见 INF-28）。
- 通过 `Blueprint` 宏复用：`tenant()`、`user()`、`no()`、`cover()`、`pictures()`、`easyStatus()`、`sort()`、`regionAddress()`（`AppServiceProvider::bootBluePrint()`）。
- 金额统一 `decimal(12, 2)`（Laravel `decimal($column, 12)` = 12 位总长、2 位小数），方向正确。

### 4.2 主要问题

| 编号 | 问题 | 位置 | 影响与建议 |
|---|---|---|---|
| DB-01 | 全库几乎无外键 | `database/migrations/*` | 仅 `payment_refunds.payment_order_id`、`delivery_rules.delivery_id` 有外键。删除用户/订单/商品后大量孤儿数据（`order_items`、`refund_items`、`coupon_user`、`user_account_logs`），无法靠数据库兜底。建议核心资金/订单链路补 `constrained()->cascadeOnDelete/restrictOnDelete`。 |
| DB-02 | `refunds.no` 非唯一 | `0003_02_00_000002_create_refunds_table.php:20-21` | 与 `payment_orders.no`、`payment_refunds.no` 的 `unique` 不一致，退款单号可重复，直接影响财务对账。建议加 `unique`。 |
| DB-03 | `coupon_user` 无 `(user_id, coupon_id)` 唯一约束 | `0003_03_00_000001_create_coupons_table.php:76-91` | 「每人限领 N 张」只能靠应用层计数，并发领取可超发。建议加唯一键或用 `user_id+coupon_id+seq` 唯一。 |
| DB-04 | `payment_orders` 无 `(paymentable_type, paymentable_id)` 唯一约束 | `0004_00_00_000001_create_payments_table.php:13-49` | 同一订单/充值单可创建多张支付单，是 FIN-04 重复入账的前提。建议加唯一索引（或前置关闭旧单）。 |
| DB-05 | `tenant_id` 普遍可空 | 各业务表 | 允许「无租户全局数据」，与「租户隔离」目标冲突（Finance FIN-01 即由空租户放大）。建议非平台级表统一 `not null`。 |
| DB-06 | `user_accounts` 无 `tenant_id` | `create_user_accounts_table.php:14-38` | 钱包全局共享，与充值/退款按租户统计冲突；需明确「钱包是平台级还是租户级」并落在注释/文档。 |
| DB-07 | `withdraw_orders` 无 `tenant_id` | `create_user_accounts_table.php:123-129` | 与 `recharge_orders` 口径不一致（FIN-06）。 |
| DB-08 | 软删除与唯一索引混用 | `orders.no`、`payment_orders.no` 等 | 删除后单号不可复用，通常可接受；但 `refunds` 既无唯一又软删，语义最混乱。建议统一「单号永不复用 + 唯一索引 + 软删仅作业务作废」。 |
| DB-09 | 时间类型不统一 | 各表 | 混用 `timestamp`/`dateTime`；无 `timestamptz` 约定，部署跨时区时统计口径易错。建议统一 `timestamp` + 应用时区（见基础设施报告）。 |
| DB-10 | 迁移前缀重复 | `0000_00_00_000001_*`、`0001_00_00_000003_*` | 依赖文件名字典序，`rollback` 批次可能不符合预期。建议后续新增迁移使用唯一时间戳。 |

### 4.3 正向观察

- 订单/退款/支付都有 `tenant_id + status + created_at` 组合索引，列表查询路径有覆盖。
- `orders` 对 `user_id+status+created_at`、`pickup_code`（唯一）设计合理。
- 金额列统一 `unsigned + decimal`，避免负值写入。
- `event_logs`、`api_logs`、`schedule_run_logs` 都有 `Prunable`/清理策略。

## 五、建议

1. **把测试基线清零**：12 条过期用例要么更新断言，要么删除；3 条真实问题按对应模块修复后补回归。
2. **引入 CI**：`pint --test` + `phpunit` + `larastan`；PR 必须绿。
3. **工厂补全必填字段**，并在 CI 中加一条「factory 可创建」的冒烟测试（对所有 Factory 逐一 `create()`）。
4. **数据库约束补齐顺序**：`refunds.no` → `payment_orders(paymentable)` → `coupon_user(user_id,coupon_id)` → 核心表外键。
5. **PG 专用 SQL**：为 `jsonb`、`split_part` 等分支建立 PostgreSQL 测试任务，避免「本地绿、生产炸」。
