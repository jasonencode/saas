## 三、跨模块共性问题

### 3.1 租户隔离「非全局」，每个入口都要显式过滤
- `BelongsToTenant` 只提供 `ofTenant()` scope，没有全局作用域；Filament 资源靠面板 tenancy，API/Service/Console 全靠开发者自觉。
- 本期因此产生的漏洞：Content API（CONT-01）、PickupVerify（MALL-03）、自提点/退货地址公共接口（MALL-05）、Campaign 统计（CAMP-12）、红包支付配置（CAMP-04）、支付配置下拉（SYS-08）、`ofTenant(null)` 静默全表（FIN-01）。
- **建议**：抽一个统一的 `TenantContext`/中间件（解析 `X-Tenant-Id` 并校验用户归属），API 层默认注入；对「必须带租户」的模型在查询构造器上强制约束。

### 3.2 授权存在多条「静默放行」路径
- `->strictAuthorization(false)`：缺策略/缺方法即放行（INF-19）。
- 租户面板 3 个资源覆写 `canAccess()`，绕过 `viewAny`（SYS-02）。
- 策略批量方法 `deleteAny($user, array $recordKeys = [])` 收不到记录键，状态校验永不执行（INF-03）。
- `AuthorizesModelAccess` 对 null 用户放行（INF-05）。
- 全局 98 个模型中 **90 个 `#[Unguarded]`**、**33 个没有策略**（`Sku`、`Cart`、`UserRealname`、`Category`、`Tag` 等业务模型在列）。
- **建议**：`strictAuthorization(true)` + CI 校验「每个 Resource 都有策略」；批量动作改用 `authorizeIndividualRecords()`；统一 `checkPermission` 为 fail-closed。

### 3.3 「写而未用」的功能比缺失更危险
全仓确认以下能力**没有任何调用方/挂载点**：

| 能力 | 位置 | 风险 |
|---|---|---|
| IP 黑名单中间件 | `BlackIpList`（`bootstrap/app.php:44` 被注释） | 后台可配置但完全不生效 |
| API 日志 | `ApiRecord` | 未启用；启用即记录明文密码/响应体 |
| 访问令牌认证 | `AccessTokenAuthenticate` | token 走 query、不校验过期、租户令牌无消费方 |
| 商城开通校验 | `EnsureStoreIsOpened` | `store.opened` 别名注册但无路由使用 |
| 浏览量去重 | `TrackVisitService` | `views` 可任意刷 |
| 结算凭据 | `VoucherService::create` | 分销奖励永不发放 |
| 支付宝 | `AlipayService` + `Alipay::getConfig()` 返回 `[]` | 后台可配置，前台无入口且必然报错 |
| RSA 长文本加密 | `Support/RSA` | 分块尺寸算错，且无调用方 |
| 身份购买 | `IdentityService::purchase`/`checkAndAssign` | `is_unique` 语义未实现 |
| 短信校验 | `SmsService::verifyCode` | 找回密码链路整体缺失 |
| `OrderResult` DTO | `Services/Mall/DTOs/OrderResult` | 无引用且金额口径错误 |

**建议**：逐项决策「启用并补齐安全措施」或「删除」，不要保留半成品；在 README/架构文档中标注功能状态。

### 3.4 异常分层失效
- 所有 `RuntimeException`/`InvalidArgumentException` 统一映射 400（INF-04），`QueryException` 继承 `RuntimeException` → 生产环境可能把 SQLSTATE/表名透给客户端。
- 多个控制器 `catch (Throwable) { return ApiResponse::error($e->getMessage()); }`（订单删除/签收、推荐关系、实名）。
- **建议**：定义 `BusinessException`（400/422）与系统异常（500 + `report()`）两套出口；禁止控制器直出 `getMessage()`。

### 3.5 金额与并发
- 金额类型混用：`decimal(12,2)` + PHP 侧 `float`/`string` 交替（MALL-24、FIN-12、CAMP-11）。
- 已做得好的地方：库存条件扣减、券乐观核销、支付退款条件更新、账户行锁。
- 仍缺：充值入账无锁（FIN-04）、红包领取 check-then-act（CAMP-10）、身份编号 `max+1`（USER-10）、购物车 `firstOrCreate`（MALL-18）。
- **建议**：统一「字符串 + bcmath」；资金/库存写路径统一「事务 + 行锁/条件更新 + 幂等键」。

### 3.6 后台 UI 与领域服务脱节
- Filament 默认 `DeleteAction`/`DeleteBulkAction` 绕过 `OrderService::delete()`，不释放库存/券（MALL-06）。
- Campaign 三个资源的 `view` 页无入口，奖品池/红包码/兑奖/发券从 UI 不可达（CAMP-08）。
- 后台「订单付款」绕过 `PaymentService`（MALL-01）。
- 资金凭证（退款单、红包码、结算凭据）可被删除/编辑/级联删除（FIN-03、FIN-15、CAMP-05）。
- **建议**：后台所有「有副作用的动作」统一调用领域 Service；资金/审计类记录只允许「作废」不允许删除。

## 六、已知的「非缺陷」设计取舍

以下事项看起来像问题，但属于有意的设计，建议在文档中固化而不是修改：

1. `ApiResponse::success()` 不包 `data` 层（AGENTS 已声明）。
2. `BaseCollection` 使用 `list`/`page` 而不是 Laravel 默认 `data`/`meta`。
3. `#[Unguarded]` + 表单层白名单（风险在表单遗漏，不在机制本身）。
4. `->strictAuthorization(false)` + 「每个资源必须补策略」的团队约定。
5. 计划任务全部 `->onOneServer()`（生产要求 Redis 缓存锁）。
6. 金额列 `unsigned`，不允许负值写入。
