# 基础设施与框架层 检查报告

- **检查日期**：2026-11-01
- **检查范围**：`bootstrap/app.php`、`app/Providers`、`app/Http/Middleware`、`app/Http/Handlers`、`app/Http/Responses`、`routes/*`、`app/Support/*`、`app/Console`、`database/migrations`、`config/*`、`phpunit.xml`
- **检查方式**：全量静态走读 + 全量测试（`php artisan test`：1134 passed / 17 failed / 1 skipped，耗时 238s）+ 关键路径调用链验证
- **结论**：框架骨架整体设计清晰（双面板、策略矩阵、统一异常、日志中心、调度留痕都做得较扎实），但存在 **4 类系统性问题**：
  1. 若干安全中间件/功能「写了但没接上」（黑名单、API 日志、商城开通校验、访问令牌认证）；
  2. 授权存在「静默放行」路径（策略批量方法收不到记录、`checkPermission` 对空用户放行、`strictAuthorization(false)`）；
  3. 业务异常与系统异常共用 `RuntimeException → 400`，排障与可观测性受损；
  4. 加密、上传、令牌等敏感链路缺少必要的安全约束。

## 三、严重问题

### INF-01 商城开通校验中间件从未挂载，`store.opened` 形同虚设

- **位置**：`bootstrap/app.php:36`（仅注册别名）、`app/Http/Middleware/EnsureStoreIsOpened.php`
- **代码**：
  ```php
  // bootstrap/app.php
  'store.opened' => EnsureStoreIsOpened::class,
  ```
  ```php
  // 全仓库检索：除 bootstrap/app.php 的别名外，没有任何路由或中间件组使用 'store.opened'
  ```
- **影响**：`EnsureStoreIsOpened` 会检查 `StoreConfigure::isOpened()`，但没有任何 API 路由挂载它。未开通/已关闭商城的租户，其商品、下单、支付接口仍然完全可用，与注释「未开通时统一返回 403」的设计目标相反。
- **建议**：在 `routes/apis/mall.php` 的商城业务路由组统一追加 `store.opened`（或按租户在服务层强制校验），并补充 Feature 测试覆盖「未开通租户访问返回 403」。

### INF-02 `/sse` 公开接口泄露全站评论，且响应头拼写错误导致 SSE 不可用

- **位置**：`routes/web.php:13`、`app/Http/Controllers/System/SseController.php:29`、`:62`
- **代码**：
  ```php
  $router->get('/sse', [SseController::class, 'index']); // 无任何鉴权
  ```
  ```php
  $records = Comment::where('id', '>', $lastId)   // 未过滤 status / tenant / 审核状态
      ->orderBy('id')
      ->get();
  ```
  ```php
  'Contents-Type' => 'text/event-stream',   // 应为 Content-Type
  ```
- **影响**：
  1. 任何人可访问 `GET /sse?last_id=0` 并持续拉取**所有租户、所有状态（含未审核/隐藏）**的评论正文与 ID；
  2. `Contents-Type` 拼写错误，浏览器不会进入 EventSource 模式，SSE 实际不可用；
  3. 每 0.8s 全表增量 `get()`，`last_id=0` 时会把历史评论一次性读出，存在内存与数据库压力。
- **建议**：路由加 `auth:sanctum` 与租户上下文；查询补 `status`（审核通过）与 `tenant_id` 过滤、`limit`；修正响应头；评论量上来后改为队列 + 广播，而不是数据库轮询。

### INF-03 批量删除授权锁失效：策略 `deleteAny()` 永远收不到记录主键

- **位置**：`app/Policies/Mall/OrderPolicy.php:60-72`、`app/Policies/Mall/RefundPolicy.php:56-66`
- **代码**：
  ```php
  public function deleteAny(Authenticatable $user, array $recordKeys = []): bool
  {
      if (!empty($recordKeys)) {
          foreach ($recordKeys as $key) {
              $order = Order::where('no', $key)->first();
              if (!$order || !in_array($order->status, [...], true)) {
                  return false;
              }
          }
      }
      return $user->hasPermission(__CLASS__, __FUNCTION__);
  }
  ```
- **事实依据**：Filament 5 的 `Resource::getDeleteAnyAuthorizationResponse()` 调用的是 `getAuthorizationResponse('deleteAny')`，**只传当前用户**；`DeleteBulkAction` 默认不逐条鉴权（源码 `vendor/filament/actions/src/DeleteBulkAction.php` 直接 `$record->delete()`）。
- **影响**：`$recordKeys` 恒为空数组 → 状态校验分支永远不执行 → 只要拥有「批量删除」权限，就能批量删除**任意状态**的订单/退款单（例如待付款、已支付订单），绕过单条 `delete()` 的状态限制。
- **建议**：改用 Filament 的 `->authorizeIndividualRecords('delete')`（在 Resource 的 Table/BulkAction 上配置），或把状态校验放进 Action 的 `->action()` 内逐条判断，不要依赖 `deleteAny` 的第二个参数。

## 四、高优先级问题

### INF-04 `RuntimeException` 一律映射为 400，系统错误被伪装成业务错误

- **位置**：`app/Http/Handlers/ApiExceptionHandler.php:42-43`、`:58-61`
- **代码**：
  ```php
  $exception instanceof InvalidArgumentException,
  $exception instanceof RuntimeException => self::handleBusinessException($exception),
  ```
- **影响**：
  - 数据库异常、`firstOrFail()` 之外的运行时错误、`openssl`/文件系统错误等多以 `RuntimeException` 抛出，会被返回 **400 + 原始 message**；
  - 客户端会误判为参数错误而不重试，监控也统计不到 5xx；
  - 生产环境可能把内部实现细节（SQL、路径、密钥名）透出给调用方。
- **验证**：`LotteryApiTest > draw returns 422 when draws exhausted` 实际返回 400，即该映射把「业务规则失败」和「参数校验失败」混为一谈，测试预期也因此长期失败。
- **建议**：引入 `App\Exceptions\BusinessException`（或既有 `OrderNotPayableException` 模式），只把明确的业务异常映射为 400/422；其余 `Throwable` 走 500 并 `report()`。

### INF-05 用户归属校验对 `null` 用户直接放行（越权读取）

- **位置**：`app/Http/Controllers/Traits/AuthorizesModelAccess.php:20-32`
- **代码**：
  ```php
  if (!$model->user || $model->user->is(Auth::user())) {
      return;   // 没有 user 关联时不鉴权
  }
  ```
- **影响**：订单、支付单、地址、退款等凡是复用该 trait 的资源，只要 `user` 关联为 `null`（用户被硬删除、历史脏数据、模型缺少 `user()` 关系），任意登录用户都能读取/操作该资源，属于 IDOR。
- **建议**：改为「无 user 关联 = 拒绝」，并区分 `hideExistence`：
  ```php
  if (!$model->user || !$model->user->is(Auth::user())) { /* 抛 404/403 */ }
  ```

### INF-06 AES-CBC 无完整性校验，实名/银行卡等 PII 可被篡改

- **位置**：`app/Support/AES/AES.php:13-18`、`:30-47`
- **代码**：
  ```php
  private const string CIPHER = 'AES-256-CBC';
  // 密文格式：base64(iv)|base64(ciphertext)，无 MAC / GCM tag
  ```
- **影响**：CBC 无认证，攻击者拿到密文后可做 padding oracle 或位翻转；解密端只校验格式，不校验来源，篡改后可能得到攻击者期望的明文（如把他人身份证号替换）。
- **建议**：改用 `AES-256-GCM`（`openssl_encrypt(..., 'aes-256-gcm', ..., $tag)`）并把 tag 与 iv 一起存储；或对 `iv|ciphertext` 追加 HMAC-SHA256（encrypt-then-MAC）。

### INF-07 后台「获取令牌」在弹窗打开瞬间签发永久 Token

- **位置**：`app/Filament/Actions/User/GenerateTokenAction.php:28`
- **代码**：
  ```php
  $this->fillForm(fn (User $record) => [
      'token' => $record->createToken('T:0')->plainTextToken,
  ]);
  ```
- **影响**：
  1. 只要打开弹窗（甚至误点）就会在 `personal_access_tokens` 落一条**无过期时间**的令牌，取消弹窗也不会回收；
  2. 管理员可为任意用户签发长期令牌，无二次确认、无审计日志，令牌明文展示在页面；
  3. 与「敏感操作需输入当前密码」的 `ConfirmsCurrentPassword` 约定不一致。
- **建议**：改为显式提交按钮后再 `createToken`，设置 `expiresAt`（如 24h）与最小 abilities；记录 `event_logs`；必要时要求当前密码。

### INF-08 图片上传无大小上限，且把每次上传明细写入日志

- **位置**：`app/Http/Requests/UploadRequest.php:23-24`、`app/Http/Controllers/System/UploadController.php:31`
- **代码**：
  ```php
  'mimes:jpg,jpeg,png,gif,bmp,webp',
  // 'max:'.config('storage.FRONT_MAX_FILE_SIZE'),   // 被注释
  ```
  ```php
  info($info);   // 每个上传都写一条 info 日志（含路径、大小、原始文件名）
  ```
- **影响**：
  - 单请求可上传任意大的图片（受 PHP `upload_max_filesize` 兜底），配合 `images` 多文件接口可放大为存储/内存 DoS；
  - 每张图片写一条 info 日志，日志量与 PII（原始文件名）外泄风险。
- **建议**：恢复 `max:` 校验（如 5MB）并同步 `UploadsRequest`；删除 `info($info)`，需要审计就写 `EventLogService`。

### INF-09 全局信任所有代理，IP 限流与黑名单可被伪造头绕过

- **位置**：`bootstrap/app.php:33`
- **代码**：
  ```php
  $middleware->trustProxies(at: '*');
  ```
- **影响**：`X-Forwarded-For` 可任意伪造，`$request->ip()` 随之变化。按 IP 的 `login` / `sms` / `register` 限流、IP 黑名单、登录记录、支付回调 IP 全部可被绕过或污染。
- **建议**：`at` 配置为实际反代网段（或从 `config('custom.trusted_proxies')` 读取）；仅在确认有可信入口时使用 `*`。

### INF-10 后台「清缓存」组件无任何权限校验

- **位置**：`app/Livewire/Filament/ClearCache.php:14-27`（渲染于 `BackendPanelProvider` 的 `GLOBAL_SEARCH_AFTER`）
- **代码**：
  ```php
  public function clear(): void
  {
      Artisan::call('optimize:clear');
      Artisan::call('modelCache:clear');
      ...
  }
  ```
- **影响**：任何能进入 backend 面板的账号（不要求超级管理员、不要求 `Settings` 权限）都可一键清空生产缓存；高并发下会造成缓存击穿。另外 `modelCache:clear` 若未安装对应包会抛异常，前端只看到失败。
- **建议**：用 `userCan()`/策略限制为系统管理员；增加二次确认与操作日志；确认命令存在后再调用（`Artisan::call` 前 `$this->hasCommand()` 或 try/catch）。

## 七、数据库与配置层面的补充观察

1. **时区不一致**：`.env.example` 为 `APP_TIMEZONE=UTC`，而 `FilamentPanelProvider` 设置 `FilamentTimezone::set('Asia/Shanghai')`。所有 `whereDate('created_at', today())` 统计（后台看板、AI 工具、抽奖次数）都按应用时区计算，若生产沿用示例值，中国区「今日」会错位 8 小时。
2. **金额类型混用**：`decimal(12)` 存储 + PHP 侧 `float`/`string` 交替（`Order::getTotalAmount()` 返回 `float`，`DeliveryService` 返回 `string`）。建议全链路统一「字符串 + bcmath」，避免 JSON 输出 `13` 与 `13.00` 漂移（详见 Mall 报告）。
3. **软删除与唯一索引**：`orders.no`、`payment_orders.no` 为唯一索引且模型启用 `SoftDeletes`，删除后同号无法复用（通常可接受），但 `refunds.no` 连唯一都没有，建议统一策略。
4. **测试基线**：全量测试 17 个失败，其中至少 15 个是**测试数据/断言过期**（见 `09-测试与数据库检查.md`），长期红灯会掩盖真实回归，CI 实际上失去了守门作用。
