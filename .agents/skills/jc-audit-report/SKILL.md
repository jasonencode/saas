# 代码检查/审计报告规范

对代码库、模块、服务链路做检查后输出报告，并跟踪修复结果。适用于任何技术栈。

## 1. 适用场景

* 按模块/服务出具检查报告
* 汇总问题清单并按 P0–P3 分级（按通用标准：P0 最严重 → P3 最轻）
* 修复完成后把修复结果回填进报告（汇总表 + 明细状态）
* 跨轮次检查时定位上一轮问题的当前状态

## 2. 报告结构与存放

* 存放位置遵循项目现有文档惯例；无惯例时建议 `docs/reviews/<YYYY-MM-DD>/`，总览一份 + 各模块分文件
* 报告头部固定包含：**检查日期 / 检查范围 / 检查方式 / 测试基线 / 与上一轮关系**
* 测试基线写实跑命令与结果；报告列出的问题需说明是否在测试绿灯下存在
* 只做检查不改代码时，明确声明“未修改任何业务代码”

## 3. 汇总表格式（含修复结果列）

每份报告以汇总表开头，**每个单元格用 `已修复/发现数` 记法**：

```markdown
| 模块 | P0 | P1 | P2 | P3 | 修复结果 | 一句话结论 |
|---|---:|---:|---:|---:|---|---|
| 权限与后台动作 | 0/0 | 0/0 | 2/2 | 1/1 | 3/3 | 敏感动作已补权限点，批量改门店已收敛 |
| 订单与状态流转 | 0/0 | 3/4 | 5/7 | 1/2 | 9/13 | 押金 0 卡死已修，套餐编辑回归待排期 |
| 支付与退款 | 0/0 | 0/0 | 4/6 | 1/2 | 5/8 | 分账终态已补齐，退款复审入口待排期 |
| **合计** | **0/0** | **4/7** | **24/42** | **4/12** | **32/61** | |
```

规则：

* 单元格写 `已修复数/发现数`：`1/2` 表示该级别发现 2 个问题、已修复 1 个
* 分母是**审计基线**，报告发出后不随修复变化；修复进度只体现在分子增长
* 报告初版（尚未修复）各级别写 `0/n`，如 `0/4`
* “修复结果”列写该模块跨级别的合计 `已修复/总数`；“合计”行写全报表总计
* 分子只计 ✅ 已修复；⚠️ 部分修复、⏳ 待修复、➖ 不修复均不计入分子，未修复数 = 分母 − 分子
* 有遗留时，“一句话结论”点出遗留问题的主题；遗留编号在模块明细中列出

## 4. 问题明细与状态标记

汇总表之下按模块分节，每个问题一条：

```markdown
### ORD-01 后台代付不产生支付单 [P1] ✅ 已修复

- **位置**：`src/actions/OrderPaymentAction.ts:42`
- **问题**：代付直接改订单状态，不创建支付单，订单永久无法退款
- **修复**：事务内先建支付单再走支付服务（2026-11-15）
- **验证**：`OrderOperationsTest::test_backend_pay_creates_payment_order` 通过
```

状态标记：

| 标记 | 含义 |
|------|------|
| ✅ | 已修复并验证（注明修复日期与验证方式） |
| ⚠️ | 部分修复（说明原因与遗留部分） |
| ⏳ | 待修复（注明是否已排期） |
| ➖ | 不修复（必须说明理由：设计使然/成本过高/已另有方案） |
| 🆕 | 本轮新增，尚未处理 |

## 5. 问题编号规则

* 格式：`<模块缩写>-<序号>`，如 `ORD-01`、`PAY-03`
* 编号跨轮次**稳定不复用**：复核同一问题仍用原编号并更新状态；新问题接续最大编号
* 模块缩写保持同一项目内一致，不跨项目套用

## 6. 修复结果回填流程

1. **审计出报告**：问题分级、编号、定位到文件/行号，初始状态全部记 `⏳`
2. **确认修复范围**：按 P0 → P1 → P2 给出建议修复顺序，有歧义先问，不静默决定
3. **逐项修复**：每项完成后运行项目的格式化命令与最小范围相关测试；修 Bug 先写能复现的测试
4. **回填报告**：
   * 问题状态改为 ✅ / ⚠️ / ⏳ / ➖，补充“修复”“验证”两行
   * 汇总表对应单元格分子 +1（如 `1/4` → `2/4`），并同步模块与总计
   * “一句话结论”改为**修复后的现状**，不再描述已修掉的问题
5. **复检**：跑受影响测试 + 全量基线对比，更新报告头部的测试基线与结论
6. **汇报**：列出改动文件、执行命令、测试结果、已知既有失败；**未经明确要求不提交/推送**

## 7. 与待办清单的关系

* 如项目用独立的待办/问题清单文件跟踪修复，可继续使用；**最终状态以报告回填为准**，两处不得矛盾
* 无此类文件则忽略本节

## 8. 红线

* 每个结论必须落到具体文件/行号/代码事实，不写无依据的推测
* 测试基线必须实跑，不沿用旧数字冒充
* 不删除/重命名历史文件（迁移、已发布接口等），除非用户明确要求
* 未经用户明确要求，不执行 `git commit` / `git push` / 历史重写
